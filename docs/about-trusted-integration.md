# About and trusted Lore integration (local candidate)

Issue: MusicNerdWeb #1655. This integration is local, unreleased and not live-verified.

About preparation and Lore summaries consume only approved evidence eligible under the existing source-publication policy. Explicit private, pending and rejected sources are excluded. Inherited sources require an approved claim or an exact immutable trusted-submission event; a contributor's later role loss does not remove submission-time trust. This does not grant contributors regeneration or profile-edit authority.

Lore revisions bind source identity, provenance, publication and evidence content. Under the artist lock, About and Lore publication compare the current eligible source set with the generated manifest. Onboarding document publication receives the same check. Administrator authority is held through the short write transaction. Model work never holds those locks.

Directory preparation has its own assessed-source provenance. Its public projection and claimant draft reuse preserve that contract while rejecting private or unknown publication states. Reused claimant drafts carry current revision-bearing evidence, and publication revalidates it. Claiming must not erase trusted contributions.

Public Web llms.txt requires a current claim and valid current vault revisions; it hides the whole document when recorded evidence is private, rejected, removed, revised or legacy/unversioned. Owner/admin private reads are unchanged.

Prior review boundary, addressed by the continuation below: claimed About text had no durable bio-to-evidence association. Independently refreshed artist_docs cannot prove the provenance of artists.bio or pinned history. The continuation adds explicit provenance across generated/current/history writers. This integration does not invent legacy provenance or silently hide manually authored bios. Upload/storage deadline and physical object cleanup work remains separate. Provider-free PGlite checks do not establish multi-connection production PostgreSQL concurrency or live provider behavior.

## Durable About provenance (local continuation)

Migration 0061 now creates private `mn_private.artist_bio_provenance` and `mn_private.artist_bio_version_provenance` sidecars. Public artist/history tables gain no provenance columns; missing sidecar rows represent legacy lineage. Only the migration owner and mnweb can access evidence, with RLS and explicit ACL validation. It performs no historical backfill. New server-generated output records version, exact text SHA-256, generation claim ID (or explicit unclaimed scope) and its complete evidence manifest. The write and history snapshot are atomic. Identical prose from a new generation still records new evidence. Missing generation evidence is an explicit `unknown` marker, never a legacy/null record.

Onboarding's client-edited draft is recorded as `authored`, not authenticated server-generated output. It remains claim-scoped and its supplied complete source manifest must pass the current evidence checks. In-process automatic generation and explicit regeneration record `generated`. Manual edits of provenance-bearing text retain its source restrictions and refresh the text hash; malformed or mismatched lineage stays unknown. Pins restore the exact selected version's provenance, and equal text with different evidence remains distinct history.

Public readers read text, provenance, approved claim and current eligible vault evidence together. Malformed/unknown/text-mismatched or changed/private/rejected evidence hides the public About while retaining stored/editor/history content. Claim-scoped output requires the same approved claim. Unclaimed server-generated output requires at least one source, exclusively eligible vault evidence, and safe citation URLs; it can survive later claiming while that evidence stays eligible. Authored and legacy/null output never acquires unclaimed public eligibility. No contributor regeneration or editing authority is added.

Legacy/null bios retain existing claimed-only display behavior. Their historical provenance cannot be reconstructed honestly, so this does not retrospectively certify or invalidate legacy prose. An independently authored replacement of provenance-bearing text conservatively keeps the old source restrictions; an explicit lineage-reset product action is not introduced here. The schema must be migrated before new readers/writers are deployed. New readers fail closed if an old writer changes provenance-bearing text without updating its hash, but old readers ignore provenance and old writers can still create null history. A mixed-version deployment is not privacy-safe; rollout must deploy the coordinated API/Web pair before claiming the new protection.

New history snapshots saved while correcting a directory preparation use explicit unknown provenance: directory assessment is not saved-About generation provenance. The current directory public projection is unchanged, but those new history entries cannot later bypass evidence checks by being pinned as legacy prose. They remain available to authorized editors. Reset backups include the removed current provenance with the removed text.
